# Pearl Relay v1.2.1 热修复验证报告

## 当前结论

状态：**v1.2.1 已正式发布并合入 main；生产部署待完成。**

v1.2.0 在同一玩家配置包含多个旧点时，保存新点或逐个重存旧点会把整份
文件写成 schema v2；下一次读取又因为其他旧点没有目标指纹而把混合文件
判为损坏，并从 `.bak` 回滚。结果是新点从 `list` 消失，而旧点继续返回
`RELAY_REQUIRES_RESAVE`，导致多旧点配置无法逐步升级。

v1.2.1 保持所有结构和字段校验，只允许缺少目标指纹的旧点与完整目标指纹
点在 schema v2 文件中共存。旧点仍不能直接点火，但可以逐个同名重存，不再
阻止其他点保存、列出或使用。

## 测试驱动证据

RED 阶段先增加两个生产形态测试：

1. 两个旧点存在时新增第三个完整点；
2. 两个旧点存在时只升级其中一个。

修复前目标测试共 11 项，其中新增两项均因
`RelayConfigException`/`InvalidConfigException` 失败，并进入和生产一致的
恢复路径。

GREEN 阶段只改变目标指纹校验合同：目标指纹缺失表示待升级旧点；目标指纹
一旦存在仍必须完整有效。新增命令级 GameTest 覆盖：

- 玩家简写保存第三个新点；
- `list` 同时显示两个旧点和新点；
- 同名重存第一个旧点后，第二个旧点和新点仍可列出；
- 未升级旧点继续稳定返回 `RELAY_REQUIRES_RESAVE`；
- 整个流程不产生 `.corrupt-1`。

## 审查与发布门槛

- 新增生产依赖：无。
- 配置路径、schema 版本和命令接口：不变。
- `.corrupt-N` 保持证据文件，不在热修复中自动合并。
- 回滚触发条件：启动失败、版本或哈希不符、新增配置恢复事件、命令冒烟
  失败、出现 crash report 或未知异常。
- 回滚方式：停服后恢复部署前 v1.2.0 JAR；配置备份保持原样，不回写世界或
  玩家数据。

五轴审查结论：**APPROVE**。

- 正确性：生产故障的新增、逐个升级、旧点拒绝和非法目标边界均有自动化。
- 可读性：生产实现只移除顶层 schema 对目标必填的错误耦合，并保留解释
  混合文件意图的注释。
- 架构：配置路径、数据模型、schema、命令和恢复机制均未新增分支或依赖。
- 安全性：JSON 和所有现有字段继续整文件校验；存在但非法的目标仍拒绝。
- 性能：读取和校验复杂度不变，仍为每个玩家配置的线性遍历。
