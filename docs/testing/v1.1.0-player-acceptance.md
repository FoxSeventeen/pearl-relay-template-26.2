# Pearl Relay v1.1.0 玩家实机验收

## 目的与发布门槛

本清单用于 `v1.1.0-rc.1` 的真实玩家验收。自动化与无客户端测试不能证明实际珍珠滞留装置最终完成传送，因此以下项目全部通过或由项目所有者明确批准例外后，才能发布 `v1.1.0`。

每项测试请记录：日期、服务端提交/JAR SHA-256、测试玩家 UUID、装置名、`execution` ID、结果（PASS/FAIL）和相关日志行。不要在公开报告中记录服务器密码。

## 前置条件

- 服务端为 Minecraft `26.2`、Java `25`、Fabric Loader `0.19.3+`、Fabric API `0.152.2+26.2`、Carpet `26.2`。
- 安装待验收的 `pearlrelay-1.1.0-rc.1.jar`，并确认 `/pearlrelay test` 返回 `Pearl Relay command works.`。
- 准备一套可工作的真实珍珠滞留装置；激活方块必须能被站在保存的出生坐标处的生存模式玩家右键触及。
- 准备两个不同 UUID 的真实玩家账号 A、B；测试区有管理权限或管理员协助。
- 为每次触发保留服务端 `logs/latest.log`，用 `grep 'event=relay_fire' logs/latest.log` 查找证据。
- 记录装置目标方块所在区块。只有该区块内、所有者为命令执行玩家的末影珍珠才计数。

建议名称：

```text
玩家 A：accept_a
玩家 B：accept_b
旧版配置：legacy_v1
```

保存命令中的坐标按实际装置替换：

```mcfunction
/pearlrelay save accept_a <dimension> <spawnX> <spawnY> <spawnZ> <lookX> <lookY> <lookZ>
```

## 1. 有效中继的保存、列出、触发和删除

步骤：

1. 玩家 A 面向已加载、未遮挡且在交互距离内的装置目标，执行上面的 `save accept_a`。
2. 执行 `/pearlrelay list`。
3. 确保玩家 A 的珍珠位于目标区块，执行 `/pearlrelay fire accept_a`。
4. 等待完成消息，再执行 `/pearlrelay remove accept_a` 和 `/pearlrelay list`。

通过标准：

- `save` 返回目标方块类型和坐标；`list` 包含 `accept_a`。
- `fire` 返回 `Relay queued` 和执行 ID，随后返回同一 ID 的 `completed`。
- `remove` 成功，最终列表不再包含该名称。

失败标准：任一步无消息、错误名称、错误执行 ID、移除后仍可见，或服务端产生异常。

## 2. 真实珍珠装置完成传送

步骤：

1. 重新保存 `accept_a`，按装置正常流程放入玩家 A 自己的珍珠。
2. 让玩家 A 站在预期传送起点并执行 `/pearlrelay fire accept_a`。

通过标准：玩家 A 被装置中的珍珠正确传送，且日志终态为 `result=completed`。

失败标准：模组报告完成但珍珠未释放、错误玩家被传送、传送位置错误，或出现额外珍珠操作。

## 3. 假人的出生、看向、单次使用和退出

步骤：

1. 让另一名观察者站在测试区，执行一次有效 `fire`。
2. 观察生成名为 `pr_<短UUID>_<名称片段>` 的假人及目标装置。
3. 检查日志中的 `accepted` 和 `terminal`。

通过标准：假人只出现一次，位于保存的出生位置，朝向目标，只右键一次，并在完成后退出；装置不会被双击。

失败标准：位置/朝向错误、使用零次或多次、出现两个假人、终态后仍能看到假人。

## 4. 相同方块类型的状态变化仍然有效

步骤：

1. 用拉杆、活板门等有可变状态的目标保存中继。
2. 手动改变其开关、朝向以外的可变状态（不得把它换成另一种方块）。
3. 保持玩家 A 的珍珠有效并执行 `fire`。

通过标准：预检通过，假人仍只使用一次；不得返回 `TARGET_BLOCK_CHANGED`。

失败标准：只因同类型方块状态变化而拒绝。

## 5. 目标方块类型改变时在生成假人前拒绝

步骤：

1. 保存有效中继后，把目标替换成另一注册表类型或空气。
2. 保持目标区块已加载并执行 `fire`。
3. 立即检查在线玩家列表和日志。

通过标准：消息包含 `[TARGET_BLOCK_CHANGED]`；日志只有 `action=rejected`；没有对应假人登录或残留。

失败标准：假人出现、产生 `accepted`、返回其他原因，或自动恢复/修改目标方块。

## 6. 目标区块已加载但执行者没有珍珠

步骤：

1. 使用 `/forceload`、观察者或其他明确方式保持目标区块加载。
2. 移除玩家 A 在该区块的所有末影珍珠实体，但不改变装置目标。
3. 执行 `fire`。

通过标准：消息包含 `[OWNED_PEARL_NOT_FOUND]`；日志 `pearl_count=0 action=rejected`；没有假人出现。

失败标准：错误地接受、自动创建/移动珍珠，或因区块未加载返回别的错误。

## 7. 只有其他玩家的珍珠不能满足检查

步骤：

1. 保持目标区块加载，仅让玩家 B 的末影珍珠存在于目标区块。
2. 玩家 A 执行自己的 `fire accept_a`。

通过标准：返回 `[OWNED_PEARL_NOT_FOUND]`，且没有假人。

失败标准：把玩家 B 的珍珠计入玩家 A、触发装置或改变任一珍珠。

## 8. 多颗执行者珍珠允许触发但不选择珍珠

步骤：

1. 在目标区块放置至少两颗属于玩家 A 的有效末影珍珠。
2. 记录它们的位置和数量，执行一次 `fire`。
3. 对照日志中的 `pearl_count`。

通过标准：预检接受；`pearl_count>=2`；假人仍只点按目标一次；模组没有移动或指定某一颗珍珠。

失败标准：因多颗珍珠而拒绝、执行多次使用，或模组直接选择/移动珍珠。

## 9. 未加载区块被拒绝且不会自动加载

分别测试目标区块和假人出生区块：

1. 移除珍珠和其他区块票，使待测区块不再处于实体可 tick 状态；用服务端区块/票据检查工具确认。仅作为相邻票据缓存的低状态区块也应视为未加载。
2. 从另一个已加载区域执行保存好的 `fire`。
3. 再次检查该区块加载状态、区块票和实体列表。

通过标准：

- 目标/射线路径区块卸载时返回 `[TARGET_CHUNK_UNLOADED]`。
- 仅出生区块卸载时返回 `[SPAWN_CHUNK_UNLOADED]`。
- 前后均没有新增区块票、区块生成、假人或珍珠。

失败标准：命令导致区块加载/生成、假人出现，或静默失败。

## 10. 出生点受阻或视线受阻时准确拒绝

出生阻挡：

1. 在保存的假人身体碰撞箱位置放置实体方块，保持相关区块加载。
2. 执行 `fire`。

视线阻挡：

1. 清空出生位置，在眼睛到目标之间放置另一方块。
2. 执行 `fire`。

通过标准：前者返回 `[SPAWN_POSITION_BLOCKED]`，后者返回 `[TARGET_UNREACHABLE]`；两者都不创建假人。

失败标准：错误码互换、假人出现或穿过遮挡点按。

## 11. 快速重复触发不会创建重复执行

步骤：

1. 准备有效装置和玩家 A 的珍珠。
2. 在第一次任务完成前快速连续执行两次 `/pearlrelay fire accept_a`。

通过标准：第一次最多创建一个假人；第二次返回 `[EXECUTION_ALREADY_ACTIVE]`；最终没有假人残留。

失败标准：两个同名假人/执行同时运行、装置被多次点按，或第二次静默成功。

## 12. 生成假人后的失败仍然清理

步骤：

1. 准备有效装置，在执行第一条 `fire` 后、假人使用前，由第二名管理员立即移除或替换目标方块。
2. 等待执行终态并检查在线玩家和日志。

通过标准：终态为 `failed`，失败码为 `TARGET_BLOCK_CHANGED` 或实际发生的明确执行错误；生成的中继假人随后退出；只有一个终态。

失败标准：假人残留、仍点按错误方块、没有终态或出现多个终态。

## 13. 重启后 v2 配置持久化且无孤儿假人

步骤：

1. 保存 `accept_a`，记录 `config/pearlrelay/players/<UUID>.json` 中的 `schemaVersion: 2` 和目标指纹。
2. 正常停止并重启服务器。
3. 执行 `list`，重新准备珍珠并执行 `fire`。

通过标准：配置内容和名称保留；触发成功；重启前后均无 `pr_` 中继假人残留。

失败标准：配置丢失/降级、需无故重存、或重启后出现孤儿假人。

## 14. 旧版 v1 配置保留但要求重存

步骤：

1. 在停服状态下备份并放入一份真实旧版配置（没有 `target` 指纹），再启动服务器。
2. 玩家执行 `list` 和 `fire legacy_v1`。
3. 在正确装置旁用同名执行 `save legacy_v1 ...`，再准备珍珠并触发。

通过标准：旧名称仍可列出；首次触发返回 `[RELAY_REQUIRES_RESAVE]` 且无假人；同名保存后 JSON 升级为 v2，随后可触发。

失败标准：旧配置被删除、首次触发创建假人、错误消息不要求重存，或升级丢失其他中继。

## 15. 两个真实玩家的配置与列表隔离

步骤：

1. 玩家 A 保存 `accept_a`，玩家 B 保存 `accept_b`。
2. 两人分别执行 `list`。
3. 两人尝试补全或触发对方名称。

通过标准：每人只看到自己的名称；触发对方名称返回 `[RELAY_NOT_FOUND]`；磁盘上使用不同 UUID 文件。

失败标准：能看到、补全或触发他人的中继，或写入同一个玩家文件。

## 16. 玩家消息、日志和实际结果一致

对以上每个样例检查：

1. 记录玩家消息中的错误码或执行 ID。
2. 在服务端运行 `grep 'event=relay_fire' logs/latest.log`。
3. 按 `execution_id` 关联日志。

通过标准：

- 预检拒绝：恰好一条 `action=rejected`，`failure_code` 与玩家消息和实际原因一致，没有 `accepted/terminal`。
- 接受执行：恰好一条 `action=accepted` 和一条同 ID 的 `action=terminal`。
- 成功终态为 `result=completed failure_code=none`；失败终态包含真实失败码和非负 `duration_ticks`。
- `relay`、`player_uuid`、`bot`、`dimension`、`target_chunk` 和 `pearl_count` 与实际测试一致。

失败标准：缺日志、关联 ID 不同、终态重复、错误码与实际不符，或日志泄露密码/完整配置内容。
