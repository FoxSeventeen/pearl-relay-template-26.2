# Pearl Relay v1.1.0 验收边界

## 结论

原先的 16 组强制玩家实机回归已由 JUnit、Fabric 服务端 GameTest、真实
Fabric Client GameTest、生产发布 JAR 客户端 GameTest 和隔离服务端证据
替代。日常开发、拉取请求、候选版本回归以及通用环境下的稳定版发布，不再
要求真人玩家重复执行这些机械步骤。

项目所有者已于 2026-07-28 批准本修订边界。稳定版候选仍需依据同一提交
和 JAR 哈希下的完整自动化证据作最终发布决定。只有在发布声明包含指定
整合包、代理、权限系统或主观体验承诺时，才增加一次短小的探索性检查。

## 为什么当前不需要两个原生客户端

Pearl Relay 是服务端 mod，没有客户端入口、客户端存储或自定义客户端网络
协议。玩家隔离只取决于服务端命令源中的 UUID、每 UUID 配置文件、命令补全
和命令执行结果。

命令级 GameTest 使用两个独立、已注册的 `ServerPlayer` UUID 经过真实
Brigadier dispatcher，覆盖了这些边界。第二个原生客户端只会重复相同服务端
身份输入，当前没有已知缺陷、政策要求或客户端状态使其产生新的证明力。

如果以后增加客户端 mod、客户端缓存、自定义网络协议、代理身份转换、权限
mod 集成或两个连接之间的实时竞态，应重新开启多原生客户端评估。

## 保留的探索性检查

探索性检查不重复上表的机械断言，也不替代自动化。它只用于自动化无法给出
客观结论的范围：

- 玩家是否认为消息措辞清楚、反馈节奏自然；
- 假玩家的短暂出现是否在目标玩法中造成视觉干扰；
- 项目明确声称支持的整合包、代理、权限系统或监控插件是否存在兼容问题；
- 真实网络和服务器负载下是否有值得调查的主观卡顿。

规则：

1. 日常开发、PR 和 RC 回归不运行探索性检查。
2. 只有发布包含上述体验或兼容性声明时，稳定版前运行一次，建议不超过
   10 分钟、一个玩家即可。
3. 没有指定兼容性声明时，项目所有者可以记录“不需要”，自动化门槛即为
   完整技术验收。
4. 探索性发现必须转化为可复现问题；能自动化的回归应先增加测试，再决定
   是否阻断发布。
5. 不在 CI 或公开报告中保存 Minecraft/Microsoft 账号凭据、服务器密码或
   私有地址。
